# P3 记忆算法与会话管理

本阶段交付艾宾浩斯调度器、学习会话状态机，以及**已在真实 JVM 上跑通的验证测试**。

## 一、算法：SM-2 简化变体

### 为什么不用"纯艾宾浩斯"

艾宾浩斯遗忘曲线只描述**遗忘速度**（20 分钟忘 42%、1 天忘 66%…），
它不回答"每个词该怎么排"这个问题。真正可用的调度算法需要在它之上加两样东西：

1. **间隔序列** —— 答对次数越多，下次复习间隔越长
2. **难度系数 EF** —— 每个词独立维护，难词复习更频繁

只有序列没有 EF，「一遍就记住的词」和「反复忘的词」会走同一节奏。

### 间隔序列

```
索引(连续答对次数):  0   1   2   3   4    5    6    7     8
间隔(天):            0   1   2   4   7   15   30   60   180
```

参考艾宾浩斯关键节点（20 分钟 / 1 小时 / 9 小时 / 1 天 / 2 天 / 6 天 / 31 天）
做了移动端工程化压缩：**第一天内不重复出题**——用户不会 20 分钟后再打开 APP。

### 状态机

```
NEW ──首次作答──► LEARNING ──连续答对2次──► REVIEWING ──间隔≥60天──► MASTERED
                     ▲                          │
                     └─────────答错─────────────┘
```

### EF 的两条关键规则

| 事件 | EF 变化 | 说明 |
|---|---|---|
| 答对 | +0.1（上限 2.8） | 缓慢上升，避免简单词间隔无限膨胀 |
| 答错 | −0.2（下限 1.3） | **不清零**，保留"这个词难"的信息 |

**答错为何不清 EF**：如果清零，这个词之后答对时又会按新词节奏走，
无法体现"我在这词上栽过跟头"。保留下调后，难词间隔增长更慢。

### ⚠️ 一个必须封顶的地方（开发中实际踩到）

第一版实现是：

```kotlin
val effectiveDays = (baseInterval * newEase / DEFAULT_EASE).toInt()
```

看似合理，实际是**双重增长**：序列本身已体现难度递进，
再乘 EF 会让第 8 次答对变成 `180 × 2.8/2.5 = 201 天`，
超出序列上限，也让"已掌握"判定与真实间隔脱节。

**修正**：把结果封顶在序列值。

```kotlin
val scaled = (baseInterval * newEase / DEFAULT_EASE).toInt()
val effectiveDays = scaled.coerceIn(1, baseInterval)   // ← 封顶
```

封顶后 EF 的语义变得清晰：**它只能让间隔变短，不能变长**。
EF < 2.5（这个词错过）→ 间隔短于序列；EF ≥ 2.5 → 拿满序列值。
实测：易词（EF 2.80）15 天，难词（EF 1.80）10 天。

## 三、会话管理

`StudySessionManager` 是一个 `@Singleton` 的状态机，通过 `StateFlow<State>` 暴露状态。

### 职责边界

| 组件 | 只负责 |
|---|---|
| `StudySessionManager` | 当前第几题、队列怎么走、答完做什么 |
| `EbbinghausScheduler` | 算下次复习时间（纯函数） |
| `Repository` | 存取 |

三者互不越界，所以调度算法能单独测试，会话流程也能脱离数据库测试。

### State 结构

```kotlin
data class State(
    val isLoading: Boolean,
    val cards: List<StudyCard>,
    val currentIndex: Int,
    val isFlipped: Boolean,      // 卡片翻面
    val correctCount: Int,
    val answeredCount: Int,
    val isFinished: Boolean,
    val summary: SessionSummary?,
    val error: String?
)
```

派生属性 `currentCard` / `progress` / `remaining` 都是计算属性，
不占状态、不会因冗余字段不同步。

### `answer()` 一次调用做四件事

1. 算并写入艾宾浩斯进度
2. 答错则自动收进生词本
3. 写统计（明细 + 当日汇总）
4. 推进队列、必要时把错词追加到队尾

**`isNewLearned` 的判定**：用 `progressWritten` 集合记录本轮已写过的词，
只有该词**首次作答**时才计为"新学"。否则一个词答错后重现会被重复计入新学数。

### ⚠️ 队列上界（开发中实际踩到）

答错重现如果不管，用户一直答错会导致**队列无限增长、会话永不结束**。
对抗测试证实了这一点：不加上限时 1 个词能产生无数题。

**修正**：每个词最多重现 `MAX_REPEAT_PER_WORD = 2` 次。

```kotlin
val repeatTimes = repeatCount[card.wordId] ?: 0
if (repeatTimes < MAX_REPEAT_PER_WORD) {
    repeatCount[card.wordId] = repeatTimes + 1
    cards = cards + card
}
```

现在队列有了确定上界：**N 个词全部答错 = 最多 3N 题**。

## 四、学习模式与卡片装配

`StudyCard.from()` 负责把数据库对象组装成 UI 可直接渲染的卡片。

**干扰项去重**：构造选项时用 `LinkedHashSet` 并按文本排除与正确答案相同的项。
这一步不能省——同一释义可能对应多个词，否则一道选择题会有两个正确选项。

**按需查询**：只有 `FILL_BLANK` 和 `LISTENING` 才查干扰项，
单词卡片和拼写模式不查，省掉一次数据库往返。

## 五、与 P4 的接口

P4 的 UI 只需要：

```kotlin
val state by sessionManager.state.collectAsStateWithLifecycle()

// 卡片模式
sessionManager.flip()
sessionManager.markKnown()      // 认识
sessionManager.markUnknown()    // 不认识

// 选择题模式
sessionManager.answer(isCorrect = 用户选的选项 == card.meaning)
```

`StudyCard` 已包含渲染四种模式所需的全部字段，**UI 无需再碰数据库**。
